# 公開と取り消し

`main` に入った変更は、GitHub Actions（`.github/workflows/deploy.yml`）が自動でロリポップの本番サーバーへ反映する。

## 公開する

1. **了承の確認**: 依頼者が、どの PR（どの変更）を公開するかをはっきり了承していることを確認する。複数の PR があいまいなら、どれを公開するか聞く
   - 依頼の時点で「公開までおまかせ」と書かれていた場合は、その依頼で作った PR に限り了承済みとして進めてよい（AGENTS.md の0章のとおり、文章・画像・デザインの変更だけ）。自分でスクリーンショットを確認して問題がないことが条件
2. **公開前のチェック**:
   - PR の自動チェック（Build check）が成功している
   - `main` と衝突（コンフリクト）していない。衝突していたら `main` を取り込んで解決し、ビルドとスクリーンショットをやり直してから再確認をもらう
3. **マージ**: GitHub のツールで PR を `main` にマージする（通常の merge か squash。強制 push はしない）
4. **デプロイの確認**: Actions の「Deploy to Lolipop FTP」のうち、マージで作られた `main` のコミットの実行を確認する。通常1分前後で終わる
   - 成功（success）→ 5へ
   - 失敗（failure）→ ジョブのログを見る
     - `Build project` で失敗: コードの問題。直す PR を作り、依頼者に状況を説明する。本番は前の状態のまま（ビルドが失敗すると転送されない）
     - `Deploy via SSH` で失敗: 接続・パスワード・サーバーの問題。コードでは直せない。「サーバーへの接続で失敗しています。GitHub の管理者（制作担当）に、デプロイが失敗していると連絡してください」と依頼者に伝える。Actions の「Run workflow」で1回だけ再実行してよい
5. **本番の確認**: 変更したページを本番サイト（https://www.ms-works-kyoto.co.jp/ 以下）で確認する
   - 確認方法: ページを取得して変更後の文言が含まれるか見る。ただしこのサイトは JavaScript で描画するので、HTML に文言が無くても異常とは限らない。`/assets/index-*.js` が新しいファイル名に変わったか、またはスクリーンショットで確認する
   - 接続できない環境なら、依頼者にページを開いて確認してもらう（スマホで見るよう勧める。キャッシュで古い表示なら再読み込み）
6. **報告**: 「公開しました」と、変更したページの URL を伝える

## 元に戻す（取り消し）

本番で問題が見つかったとき、サーバーを直接いじらずに Git で戻す。

1. 戻したい変更（マージされた PR）を特定する。依頼者の説明があいまいなら、最近の公開を一覧にして選んでもらう
2. 最新の `main` から作業ブランチを作り、そのマージコミットを取り消す
   ```bash
   git fetch origin main
   git switch -c revert/<内容> origin/main
   git revert -m 1 <マージコミットのID>    # squash マージの場合は -m 1 を付けない
   npm run build
   git push -u origin revert/<内容>
   ```
3. 「〇〇の変更を取り消す」PR を作り、依頼者に「これを公開すると元に戻ります」と確認する
4. 了承を得たら、上の「公開する」の 3〜6 と同じ手順でマージ・確認する

急ぎで依頼者が「すぐ戻して」と言っている場合も、手順は同じ（PR を作ってマージ）。`main` に直接 push しない。

## コードを変えずに再公開したいとき

GitHub Secrets が更新されたあとなどは、Actions の「Deploy to Lolipop FTP」を「Run workflow」（ブランチは `main`）で手動実行する。GitHub のツールでワークフローを実行できる場合はそれを使ってよい（依頼者の了承を得てから）。
